# 本轮结构改造失败复盘

日期：2026-08-09

## 结论

本轮改造失败的主要原因不是代码实现，而是在目录、章节和内容类型尚未形成同一份明确结构时就开始批量修改。结果是局部内容不断追加，整本手册的组织反而更混乱，最终只能回滚。

## 后续决策

本仓库只维护模板手册，不在这里建设知识笔记、题解库或 Template / Trick /
Problem 关系系统。正文只收可复用模板、高频 snippet 和最小用法；候选调研
资料只作归档，不参与手册渲染。

## 具体失败

1. 没有先固定内容模型。

   `Template`、`Trick`、`Problem` 的关系还在讨论，就先实现了独立的 `Trick`、`Typical` 分类和双向关联。实际上 `Typical` 修饰的是题目，题目应当作为 Trick 的实例，而不是与 Trick 并列的知识类型。

2. 混淆了文件结构与标题结构。

   “一级分类分文件夹、二级分类分 `.typ` 文件”只规定物理组织，不代表每个文件都要重复一级标题。给 KMP 和 Z 函数各写一次 `= 字符串`，直接造成目录中出现两个“字符串”章节。

3. 没有按整体章节思考合并。

   用户要求合并 KMP 与 Z 函数后，正确结构应当先明确为：

   ```text
   字符串
   └── KMP
       ├── 前缀函数
       ├── Z 函数（exKMP）
       └── 使用
   ```

   实际却把“使用”分别黏在两个模板后面，仍然是在做局部拼接，而不是一个完整章节。

4. 把题目的输出协议误当成算法用法。

   P5410 中的异或权值只是为了压缩输出，不是 Z 函数或 exKMP 的核心用法。使用示例只应展示如何得到 `z` 与跨串 LCP 数组，不应抄入题目特有的校验输出。

5. 首批内容扩张过快。

   在一个章节样例尚未获得认可前，就同时移动大量文件、增加 Catalog、关系模型和渲染组件。错误因此扩散到整个仓库，也让用户难以逐项指挥。

6. 没有服从项目的主要载体。

   项目以打印稿为主要用途，却曾在正文中加入大量超链接；随后在当前只需网页预览时，又反复生成四份 PDF。两者都没有围绕当下实际需求工作。

7. 示例文字过多。

   本项目需要短定义、代码和必要用法。自动补出的长说明、元数据卡片和关系文字降低了手册的可读性。

## 下一次的工作顺序

1. 先用十行以内的文本给出目标标题树和文件路径，等待确认。
2. 只完成一个二级章节作为样板；样板通过后再批量迁移。
3. 新内容先判断能否形成 Template、Snippet 或最小 Usage；不能则不进入正文。
4. `book.typ` 统一持有一级标题，正文文件只从二级标题开始。
5. 使用章节只保留算法接口和最小调用，删除题目特有的输入输出花样。
6. 日常内容调整只更新 HTML；只有需要检查打印效果时才生成 PDF。
7. 只有修改模板代码时才做语法或定向正确性验证，纯文字调整不跑全量判题。
8. 未经明确同意绝不 push。

## 回滚状态

结构整理以前，仓库源码已恢复到在线分支 `origin/main` 的提交 `5d54d9e`；
后续改动以该基线为起点，不恢复上午被回滚的关系模型和渲染组件。
